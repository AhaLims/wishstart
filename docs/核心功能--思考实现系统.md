# 核心功能\-\-思考实现系统

1. 首页：最上面四张卡并排 —— 当前星星 / 掷骰子次数 / 今日获得星星 / 其中时间型。下面紧跟着**掷骰子**（见第 4 条）和三个快捷操作：完成任务、快速记录、抽卡。**工作时不在这里**（工时在记录页面，见下）。

   原来的「掷骰子页面」已删除，整页并进首页。那页最上面两张卡显示的就是这里的「当前星星」和「掷骰子次数」，而首页原来的「掷骰子」按钮点下去也只是跳到那页再看一遍同两个数 —— 两边信息本来就是同一份，拆成两页只多一次跳转。


2. 任务页面：
添加任务功能：任务包括两类，一种是通用型任务，另一种是时间型任务。
通用型任务：输入任务名称，限制完成次数（0或者不填就代表不限制），奖励（单选，星星or半价抽卡or免费抽卡，半价抽卡or免费抽卡都是默认只能一次的），如果奖励选择是星星，还需要填写完成一次获得的星星数量。半价抽卡是花费3颗星星抽一次奖
时间型任务：属性跟上面的通用型任务是一样的。不同的地方在于，它多一个数字字段，代表"工作多少分钟算完成 1 次"——这个数字同时是**工时折算的单位**：完成 1 次就等于干了这么多分钟（见 3. 记录页面）。比如设成 25min，完成 3 次就是 1h15min 工时。

注意：**没有计时器了**（工作时间页面已整体删除，见 3. 记录页面）。时间型任务一律靠任务页的「完成」按钮手动完成，文案写成"每 N 分钟算 1 次"而不是"自动完成"。工时则由这些完成记录在记录页面折算出来。

显示当前所有的任务，并且展示任务信息，每个任务有完成和删除按钮，点击完成按钮就会显示完成了什么任务，获得了什么东西（如果是星星就显示获得了多少颗星星，如果是半价抽卡就显示获得了免一次半价抽卡，如果是免费抽卡就显示获得了一次免费抽卡）

**这个提示用页面下方的浮窗，不弹窗**：浮窗贴在屏幕底部中间，不挡任何操作，显示「任务完成啦」+ 任务名 + 奖励，3.5 秒后自己淡出（淡出比淡入慢，是「渐进式消失」不是啪一下没了）。原来是一句 `alert()`，得手点掉才能继续，连着完成几个任务就一直被打断，体感很差 —— 见下面这条注意事项。

> **这个浮窗样式定过三轮，别再往回改**：`alert()` → 页面顶部的内嵌卡 → **底部浮窗**。「内嵌卡」那一版要在页面里占一行位置，弹出来会把下面的内容整体顶下去，连着完成几个任务时页面一直跳；而「补记碎片」那个提示条（见第 5 条）从一开始就是底部浮窗，用着最舒服，所以现在全员统一成这一种。
>
> **三处提示共用一个组件 `frontend/src/components/Toast.vue`**（任务完成 / 抽到精灵 / 补记碎片 + 转换）。以前任务页和星光值页各写了一份 `.result-card` + `.result-fade` 的 CSS，现在两份都删掉了。浮窗支持：左侧小头像（抽到精灵用，见 7.8）、可选标题行、右侧倍率小标、`error` 红色描边。

> **去掉 `alert()` 等于顺手拆掉了一道防连点。** 弹窗会把页面冻住，连点根本点不下去；换成不挡操作的浮窗之后，连点 3 下就是 3 次完成、3 份星星、3 条流水。后端对普通任务没有幂等保护（`max_complete = 0` 的本来就能重复完成），所以第一线必须挡在前端：`completingId` 非空就直接 return，请求期间所有「完成」按钮一起置灰。改这块时**别把这道判断删了**。星光值页的 `completingId` 是同一个理由（那边连点会一次任务抽走两只精灵，还破坏「不放回」）。

3. 记录页面：上方是仪表盘，显示今日总星星数，早上/下午/晚上分别获得的星星数量（都按照北京时间，早上是指6点到13点，下午是指13-18点，晚上是18-24点）。仪表盘的**下方再增加四个项：今日总计时间、早上时间、下午时间、晚上时间**，一律按「多少h多少min」显示（比如下午 3 个 25min型任务 → `1h15min`），今日总计时间就是三个时段之和。并且显示星星记录的明细。

   上面那排和下面那排**都还要多一格「其他」**（🕛）：北京时间**0点到6点**的记录归这一档。以前没有这一格，凌晨的星星被硬塞进早上或晚上——`completions.js` 塞进晚上、`records.js` 塞进早上，两处还各写了一份判据。现在判据只剩 `completions.js` 的 `getPeriod()` 一处，四个时段都从它出。

   - **「其他」那格的工时是空的**（留白，不是 `0min`）。0-6 点的工时折算口径没定，先不显示，等定了再填。
   - 因此 **早上+下午+晚上 可能小于 今日总计时间**。这是有意的：总计照旧含全部记录的工时，只是「其他」那份不单独显示。
   - 时段的**默认值按 `created_at` 现算**，但**用户手选的时段优先**。快速记录弹窗现在能自己选时段（见下面「快速记录能补记」），选完存进记录的 `period` 并打一个 `period_source: 'user'` 标记；读的时候**带上这个标记的按存的走**，没标记的照旧按 `created_at` 现算。老记录里存的那份是被上面那两套错算法写坏的（凌晨和晚上的都判错过），现算顺带把它们修回来 —— 所以这里区分的是「是不是用户亲手选的」，而不是「`period` 字段有没有值」，直接信 `period` 会把那批坏数据放回来。

**工时不单独存，每次从记录现算**（所以删记录时工时会自动跟着少）。折算口径固定：

- 「25min型任务」的每条完成记录 = **25 分钟**（按任务自己设的 `minutes_per_complete` 取，只有等于 25 的那些算）
- 快速记录里标了「⏱ 25min 型」的 = 该条**基础星数 × 25 分钟**（1 颗星 = 25 分钟）
- 其他时间型任务（比如设成 30 分钟的「运动」）**不计入工时**
- **周末加倍是奖励不是工时**，折算时必须用翻倍前的星数，否则周六的工时会凭空翻倍

因为周末那条规则不直观，**首页的「快速记录」弹窗里要把口径说出来**：选中「25min 型」时实时显示「本次 = N 分钟工时（1 颗星 = 25 分钟）」，那天是周末再补一句「星星会翻倍，但工时按翻倍前的星数算，不会跟着翻倍」。这样不用记规则，看一眼数字就知道。

> **「25min 型」就是原来的「时间型」，只是把名字说直白。** 它一个开关管两件事（星星算进掷骰子次数 + 这条按 N×25 分钟折算工时），本来就是一回事 —— 只有「25 分钟一块」的活才会既想攒次数又想知道花了多少工时。所以**别拆成两个开关**：拆了就会出现「算次数但不折算工时」这种组合，除了让人多填一次没别的用。任务那边同理，见第 2 条。

**快速记录能补记**（主要为了「前一天忘了记」）：弹窗现在有四个字段 —— 任务名称、获得星星、**日期**、**时段**，加上「是不是 25min 型」这个开关。

- **日期**默认今天，可以往前选，**不允许选未来**。往前的范围不设限。
- **时段**默认跟着当前时间自动判（跟 `getPeriod()` 同一份口径），可以改成早上 / 下午 / 晚上 / 其他 —— 四个名字跟记录页仪表盘那一排**逐字对上**，同一个桶不能两处两个名字（0-6 点那档就叫「其他」，弹窗里只加个「（0-6 点）」的注解，别改叫「凌晨」）。**换日期不会把时段重置回当前时间的那个** —— 选了就是选了；但**重开弹窗会拉回默认值**（上一次补记过哪天，留着的话下一笔会被静默补到那天）。
- **补记到过去那天时只补那一天**：星星进 `current_stars` / `total_stars` 总数，记录写进那天的记录里（记录页的时段统计和工时跟着对上），但**今天的三项计数（`today_stars` / `today_time_stars` / 掷骰子次数）一个都不动，也不发次数**。次数是「今天做了多久」的即时奖励，补记就能换次数等于可以囤次数；而过去那天的 `today_*` 是每人单份、按天重置的字段，早就随日期翻篇了，本来就回填不进去。
- **周末加倍按所选日期的星期几算**，不按今天。补上周六的记录就该翻倍 —— 不这么算的话那条的工时（用翻倍前的星数折算，见上面）会跟着一起错。
- 日期传的是 **UTC 日期串**，跟记录页的日期选择器同一套口径（整套记录系统都按 UTC 日期分桶，包括「今天」的默认值）。这里不单独改成北京时间日期，否则同一个「昨天」在两个页面会指向不同的桶。跨日边界（北京时间 0-8 点这一段 UTC 日期还停在前一天）是这套约定的固有现象，记录页一直如此。
- 补记那条在当天明细里**排在最后**：明细是按 `created_at`（也就是「什么时候录进去的」）排序的，补记的发生时间虽然是过去，录进去的时间是现在。明细上不显示时刻、只显示时段徽章（那个是按上面说的 `period_source` 算的，显示的是用户选的时段），所以顺序看着不影响什么 —— 记一笔昨天早上的事，它出现在昨天列表的末尾、徽章写「早上」。要改成按所选时段插进中间也行，那得给 zset 的 score 另编一个时间戳、让 score 和 `created_at` 分家，眼下不值得。

4. 扔骰子（**在首页上**，原来单独的掷骰子页面已删除）：要能扔骰子：扔骰子的规则为 当日**时间型**每获得五颗星星，可以额外扔一次骰子，根据点数（1到6的一个随机数）获得对应的星星。
也可以选择线下扔骰子并记录：线下掷骰子记录，如果你在线下掷了骰子，可以在这里记录并消耗1次掷骰子次数。输入点数并且记录之后也会消耗一次扔骰子的次数，并获得对应的星星数量。

注意：掷骰子次数**只认时间型的星星**，通用型任务和通用型快速记录的星星一律不算。原因是通用型任务点一下就有一颗星，拿它换骰子等于可以无限刷。
所以「快速记录」也必须让用户选这一笔是**通用型**还是**25min 型**（跟任务一样分两类），25min 型的才计入 `today_time_stars`。
页面上两个数字分开显示：「今日获得星星」（全部）和「其中时间型」（决定骰子次数的那部分），记录明细里时间型的记录带 ⏱ 标记。

排版跟着首页那套**仪表盘**走：最上面四张卡并排 —— 当前星星 / 掷骰子次数 / 今日获得星星 / 其中时间型，**下面**才是骰子和按钮。四个数里前两个是要花的，后两个是解释「次数怎么来的」，放一排就不用满页找数字。这四个数**只从 `GET /api/v1/dice` 来**（它一次给全），不再从 `/stats` 取，免得出现「卡片显示 1 次、按钮却按 0 次算」这种两处对不上。
骰子画成**真正的骰子面**（3×3 的格子，点位按点数摆，见 `Home.vue` 里的 `PIPS`），不是一个方块里写个数字；掷的时候会晃两下。**动画期间掷骰子按钮禁用** —— 不禁的话连点两下会真掷两次、扣掉 2 次机会，而页面上只显示后一次的结果，看着像少了一次。
线下补记收成了一个入口（骰子旁边的「线下掷的？自己记一笔 →」），点开是个弹窗，输入点数后记录。**没有次数时入口照样点得开，弹窗里给一句「没有掷骰子次数了 —— 当日时间型星星每满 5 颗换 1 次，用掉的不退回」**，只有「记录」是灰的。不能让入口自己也置灰：灰链接点下去什么都不发生，跟坏了没区别（真被这么报过一次「为什么用不了」）。
删记录时按同样的口径回滚：时间型的记录才回滚时间型星星，骰子次数按回滚后的时间型星星重算（用掉的不追回）。

**没有次数时要把「还差多少颗」说出来**：骰子按钮下面那行小字不能只写死规则，得带上数字 ——「没有次数了 —— 还差 2 颗时间型星星换 1 次」。线下补记的弹窗里那句同样的提示也跟着带上这个数。算法是 `5 - (todayTimeStars % 5)`，**整除时必须给 5 而不是 0**：正好是 5 的倍数说明那一档的次数已经发过了（可能已经花掉），下一次要从头攒 5 颗。这个数**纯前端算**（`todayTimeStars` 本来就在 `GET /api/v1/dice` 的响应里，见上面「四个数只从 `/dice` 来」那条），后端不用动、也不该为此新增字段。

5. 愿望页面：要能录入核心愿望（作为奖池），并且能输入愿望需要抽到多少次（也就是多少个碎片）才能合成一个完整的愿望

录入核心愿望的信息：包括愿望名称，图标，需要的碎片数量，当前已有碎片数量。

愿望页面包括四个区块：通用愿望、收集中、已完成、已过期。
收集中的愿望以卡片的方式呈现，会显示收集中愿望的图标，需要多少碎片才能合成以及当前进度是多少，并且会显示状态（收集中or已集满的状态），还有有编辑和删除的功能。编辑按钮可以点击编辑愿望的信息。对于已经集满的愿望，点击合成愿望这个愿望的状态就会进入"已完成"状态，并且转而在已完成愿望栏显示
已完成愿望：对于状态为已集满的愿望，显示图标，愿望名称，显示"已完成"的状态，显示删除按钮（点击就从已完成栏删除）

集满之后开始计时，**7 天内**必须合成，逾期转为「已过期」：碎片冻结保留（不销毁，只是不能再兑换），合成按钮消失，也不能再被抽卡抽中。已过期的愿望只能删除。

**通用愿望**：每个用户恰好一个，系统自动创建，没有碎片上限、不会过期、也不出现在「已完成」里。页面上只显示当前碎片数，不画进度条。它跟普通愿望**等权重**参与抽卡。

通用愿望的卡片上有个「**转换**」按钮 —— 它是**碎片出口的唯一入口**，点开是个弹窗，顶部先选这次要干什么，两种模式：

**模式一：实现新愿望**（原来的「实现」，只是换了文案）。填**这次实现的愿望名称**和**消耗的碎片数量**（1 ≤ n ≤ 当前持有量，可以一次用完）。确认之后：

- 通用愿望本身**留在原地继续攒**，剩余碎片不动，`realize_count` +1
- 按填的名称生成一条**新的已完成愿望**：图标固定用图标选择器里的第一个（🎁），碎片数记为 `n / n`（这次消耗了多少就是多少），直接以 `completed` 状态进「已完成」栏
- 记一条流水

**模式二：补充给已有愿望**。选一个**目标愿望** + 填**补充数量**，碎片从通用愿望**转过去**（不是凭空造）：

- 目标是**收集中且没集满**的普通愿望。已集满的（缺口为 0，没什么可补）、已过期 / 已完成的、以及通用愿望自己都不在候选里
- 数量上限是**两个数的较小者**：该目标的缺口（`total - current`）和通用愿望的当前持有量。**不能补超** —— 补超了那个愿望就溢出成负缺口了
- 补充数量默认填满缺口（缺口和持有量取小的那个），用户可以改小
- 通用愿望扣多少、目标就加多少，**1:1**
- **补满的那一刻目标直接变成 `ready`**（`markWishReady`，跟抽卡补满走同一个函数），有效期从这一刻开始算

> 为什么要有这个功能：老愿望可能长期卡在「差一颗」。普通愿望只能靠**抽卡**加碎片，而抽卡是从所有未集满的愿望里**随机**抽一个 —— 差一颗的那个愿望只能干等运气。通用愿望则是个能一直攒的桶，于是「从桶里挪一颗给老愿望」就成了补这个缺口的唯一办法。入口收在通用愿望这边（**统一出口**），而不是在每张愿望卡片上各挂一个按钮：那样碎片有两个出口（卡片上一个、通用愿望一个），迟早会长出两套校验。

5. 要能消耗星星抽卡，并且更新抽卡合成进度。抽卡有三种消耗方式：使用免费抽卡次数抽卡 / 花费半价抽卡次数 + 3颗星星抽一次卡 / 花费五颗星星抽一次卡

**抽卡入口在愿望页上**（独立抽卡页已删除）。愿望页顶部有一块抽卡面板，显示四项资源：可用星星、掷骰子次数、免费抽卡次数、半价抽卡次数，下面紧跟着消耗提示和「开始抽卡」按钮。消耗方式不用选，系统按资源自动挑一档：有免费次数就优先用免费，没有免费次数但有半价次数且星星够 3 颗就用半价，两者都没有才花 5 颗星星全价抽。面板只提前说明本次会用哪一档。

抽卡入口并进愿望页，是因为线上抽卡和「补记碎片」**共用同一套消耗档**（两处后端都调 `pickDrawMode`），拆在两页反而看不清免费/半价次数是怎么被花掉的。

确定了消耗方式之后，可以线上抽卡（会从还没集齐碎片的愿望中随机抽一个）。

线下抽卡不在抽卡面板里记录，而是到**愿望页对应愿望的卡片**上点「补记碎片」：如果你在线下抽到了某个愿望的碎片，就在那个愿望上记一笔，一次加一个碎片，消耗方式照上面的规则自动挑（跟线上抽卡是同一个 `pickDrawMode`）。**每个待实现的愿望卡片上都有一个「补记碎片」按钮**，入口只有这一处，免得两处维护两套 UI。

- 只有「收集中且未集满」的愿望能补记；已集满、已过期、已完成的卡片不显示这个按钮，后端也会拒绝。
- 按钮在请求期间会禁用，防止连点记成多个碎片；后端另外有一把按用户分的锁，保证「读资源 → 挑消耗档 → 扣资源 → 加碎片」这几步是串行的。
- 记完给一条一闪而过的提示（共用组件 `components/Toast.vue`，见第 2 条），写清楚加了几个碎片、这次消耗了什么（免费次数 / 3⭐+半价次数 / 5⭐），集满时额外提示可以合成了。

6. 统计功能：页面标题「统计 & 同步」。
- 统计累计星星数量，掷骰子数量，已完成愿望数量
- 显示星星的流水记录：什么时间完成了什么任务，获得了多少星星。或者是抽卡消耗了多少星星，获得了什么的碎片。
- **数据同步（导出快照 / 导入快照）就在这一页的最下面**。原来它是单独一个叫「设置」的页面，但那页里除了导出导入和一个只在桌面端才出现的本地路径框之外什么都没有 —— 它从来就不是「设置」，是同步；而那个路径框在桌面端删掉之后永远不会出现。两页并成一页，`/settings` 转到这一页。
- 导入完成后**要刷新页面上的数字**。快照是把整份数据换掉，不刷新的话统计和流水还是导入前那份。



7. 星光值页面：标题「星光值」。参考《洛克王国：世界》的星光值 / 许愿星 / 洛克贝做的一个独立小玩法。**这一整套（星光值、洛克贝、凝结出来的许愿星）跟任务/抽卡/骰子那套星星完全独立记账，独立运行**——不进 current_stars / total_stars，不影响抽卡，也不出现在「统计」页的星星统计和流水里。目前凝结出来的许愿星暂时不能兑换任何东西。

**页面上一共两套数，互相独立、各算各的，别把它们接起来：**

| | 星光值 | 洛克贝 |
| --- | --- | --- |
| 干什么用的 | **内部数**，喂许愿星阶梯（攒够就自动凝结出许愿星） | 玩家看的**收益数**，累计总资产 |
| 怎么来的 | 抽到精灵 → 图鉴星光值 × 2^(特殊标签数) | 抽到精灵 → 图鉴洛克贝 × 异色10 × 形态2 |
| 界面显示 | **彻底不显示**（连数字都不出现，见 7.5） | 结果卡、小卡片、详情框、流水都显示它 |

同一只精灵被抽到时会**同时**进账这两个数（一次抽卡两笔账），但两笔的规则不同、数量级也不同，**不要试图用一个去推另一个**。

7.1 星光值任务：
创建任务只需要输入**任务名称**（不再填星光值范围）；创建之后可以改名，也可以删除。
完成一次：从当天的精灵池里**随机抽一只还没抽到过的精灵**，把这只精灵对应的星光值累加到当日星光值上（见 7.6~7.8），**同时**把这只精灵对应的洛克贝累加到洛克贝总数上。
每天完成次数不限，但受当天精灵总数限制——精灵抽完了就没得抽了。

7.2 星光值（内部数，规则不变）：
只按天累计，当天没用掉的星光值第二天作废（每天清零，从 0 重新开始）。
**规则一个字没改**，只是从界面上撤下来了：以前结果卡、小卡片、进度条、流水都写星光值，现在一律不写（用户明确要求「星光值彻底不显示」）。它继续在后面喂阶梯，玩家看不见。

7.3 凝结成许愿星（自动）：
星光值一够就**自动**凝结出许愿星，同时扣掉对应的星光值——不需要手动点「凝结」。
当天凝结的第 N 颗许愿星需要多少星光值，按阶梯走：

| 当天第几颗 | 每颗需要 |
| --- | --- |
| 第 1-5 颗 | 每颗 80 |
| 第 6-10 颗 | 每颗 120 |
| 第 11-15 颗 | 160 / 200 / 240 / 280 / 320 |
| 第 16-20 颗 | 380 / 440 / 500 / 560 / 620 |
| 第 21-25 颗 | 1240 / 2480 / 4960 / 9920 / 19840 |

一天最多凝结 25 颗。档位只看「当天第几颗」，跟历史无关，每天重置。
举例：当天第 1 颗累计到 80 就凝结（扣 80），第 2 颗再攒 80、累计到 160 时凝结，第 3 颗累计到 240 时凝结……第 6 颗开始每颗要 120。

7.4 入库（**已改成自动，不再手动点**）：
凝结出来的许愿星**直接就计入总数**，不需要再点。

原来凝结完先进「待入库」区，必须点一下那排 ⭐ 才真正入库（「把星星从天上摘下来放进仓库」）。**这个步骤去掉了**：抽卡的收益要玩家多点一下才到手，体感上像被卡了一道，而且漏点就会一直挂着。

所以接口返回的状态里**没有 `pending` 了**，`banked` 就是全部许愿星。跨天行为因此简化成：许愿星总数只增不减、跨天永远保留；每天清零的只有「当天凝结了几颗」这个**档位计数**。

**注意存储里那个 `pending` 字段还留着**，恒为 `'0'`，不能当死字段删掉。它是老数据迁移的落点：改版前凝结出来的星星躺在 `pending` 里等人点「入库」，现在带不动这个步骤了，所以 `ensureStarlight()` 每次会把 `pending` 并进 `banked` 再把它写成 0（幂等）。而写回存储那一步是靠「新旧值逐字段比对」触发的，**删掉 `pending: '0'` 这一行，清零就落不了盘**，每次读都重新并一遍。用户的要求是「许愿星全留」——改规则不能让已经凝出来的星星凭空消失（线上那份数据当时天上挂着 1 颗，并进去之后总数是 8）。

`collectStars()` 和 `POST /api/v1/starlight/collect` 这条路径整个删掉了，前端那个「点一下把星星收进仓库」的按钮也一起去掉。

7.5 页面显示（**四个数 + 一片进度条，都不写星光值**）：
- **洛克贝**：当天获得 / 总共
- **许愿星**：当天获得 / 总共
- 下一颗许愿星的进度条：**只画比例，不写数字**。以前写「当天第 2 颗许愿星 40/80」，现在那个 40 和 80 是星光值，属于「彻底不显示」的范围，所以只剩一条按百分比填充的进度条 + 一句「下一颗许愿星」。今天已经凝满 25 颗时进度条换成「今天已经凝满 25 颗」。
- 今日抽到的精灵小卡片（见 7.8）
- 当日流水：**只有洛克贝**。每次抽到哪只精灵获得多少洛克贝。

流水只在本页显示，不混进「统计」页的星星流水（两套体系独立）。

**老流水（抽卡获得星光值 / 凝结消耗星光值 / 收起许愿星）一条都不删，但页面上一律不再显示**——用户要求记录里只显示洛克贝。历史还在存储里（`wishstar:starlight_logs:<userId>`），哪天想看还能查。

过滤放在**后端**（`routes/starlight.js` 组装状态时按 `unit === '洛克贝'` 滤一遍），不是在 Vue 里滤。这个接口是流水的唯一出口，放后端只写一次；放前端的话，哪天新加一个页面就得再记一次「记得把星光值滤掉」。另外「凝结不再单独记流水」也是同一件事的一半——那条流水说的就是星光值，留着它「不显示星光值」这条就没法自圆其说，凝了几颗由结果卡和「当天许愿星」那个数体现。

页面上两套数**颜色分开，一路贯到底**：许愿星是蓝的（`#7FB2FF`），洛克贝是金的（`#FFD700`，跟洛克贝图标那枚金币一个色）。总览两张卡并排放，颜色一样的话扫一眼分不出哪个是哪个。

**流水在存储里一条都不删**（那是历史记录），只是**页面上只显示最近 7 天、最多 50 条**（哪个先到算哪个）。再往前的翻不到也没人看，不必占一份响应体。历史精灵抽屉同理：每天的抽到记录都留着，页面上只显示当天的。

7.6 精灵池（数据来源）：
精灵数据来自《洛克王国：世界》wiki 图鉴的采集结果，目前放在 `C:\data\code\nrc-scraper`。
**这个路径先写死成绝对路径**（后端一个常量 + 环境变量口子），等数据拷进项目里之后再改成相对路径。

- 主表读 `data/entities.json`（814 个实体）。**旧版的 `data/spirits.jsonl` / `spirits.json` 已经不再生成，不要再读它们**——文件根本不在了，读它们等于池子是空的。
- **主键是 `id`，不是编号。** 466 个编号对应 814 个实体：同一编号下挂着本体、地区形态、首领化、异色，它们共用编号、各有独立的详情页、独立的介绍、独立的立绘。所以池子按 `id` 建，**异色 / 地区形态 / 首领化都是能单独抽到的一只**，跟本体等权。
- **星光值必须配 `starFound` 一起看**：`starFound` 为 false 时 `star` 是占位的 80，不是真值（814 条里有 136 条是这样）。光判 `star === 80` 不行——**61 条是真值 80、136 条是占位 80，混在一起分不开**。
- 自己没有值的**沿着层级往上找**，用上面那一级的：恶魔狼王（首领化，自己没值）→ 恶魔狼（本体，真值 80）→ **80**；恶魔狼王的异色 → 恶魔狼王（没值）→ 恶魔狼 → **80**。**异色跟它普通颜色那一版同分**，因为异色就是挂在那一版底下的，往上找自然找到同一级。
- 一路到顶都没有值的一共 **57 只**，也给 **80**。这一条不能省：**79 只首领化形态全部没有星光值**（异色里也有 35 只没有），给 0 会出现「抽到首领化获得 0 星光值」这种看起来像坏掉的结果。
- 这 57 只**不是**「没星光的传说精灵」，是 **wiki 上还没标星光值的那几批**：44 只集中在编号最大的 443–466（最新那一批，一直排到全池最大的 466），其余是 150–152 / 348–353 / 414–417 三个零散块。它们的介绍、属性、立绘都齐，只有星光值那一栏空着。等 wiki 补上，**重启服务就自动跟着变，不用改代码**。
- **抽到异色 / 地区形态 / 首领化时这次获得的星光值翻倍，而且身上每多一个标签就再翻一倍**：单标签 **×2**，两个标签 **×4**，三个标签叠满 **×8**。上面那几条算出来的是图鉴上的基础值，进账时按标签数乘 2 的幂。**不封顶**——封顶的话「两个标签 ×4、三个标签也 ×4」就成了要额外记的例外，而三标签的全池只有 3 只，是概率最低那一档。池子分布：×1 有 426 只、×2 有 326 只、×4 有 59 只、×8 有 3 只。
  三个标签要分开认，`form` 是**复合字段**：`lord|regional` 是「首领化 + 地区形态」两个标签，不是第三种形态（跟拼标签的 `FORM_LABELS` 一致）。异色不看 `form` 看 `kind`（异色本体的 `form` 是 `main`，地区形态的异色 `form` 才是 `regional`）。
- **抽到时的倍率要写进记录**。翻倍的规则改过（原来不管几个标签一律 ×2），老记录里存的 `star` 是**当时**实际进账的数；要是读取时按现在的规则重算倍率，前端 `star / starMultiplier` 除回去得到的基础值就跟着错。老记录没存倍率，用「进账 ÷ 图鉴基础值」反推，推不出来（图鉴值本身也改过）就当没翻倍。

**洛克贝（玩家看的那个数）：**

- 数据来自同一个 wiki 详情页里的另一个 `roco-pill`，字段是 `roco` / `rocoFound`，跟星光值并排。**采集脚本原来没抽这一项，是这次补上的**（见 7.9）。
- 上述星光值那几条**逐条照搬**，换个数而已：`rocoFound` 为 false 时 `roco` 是占位值不是真值；自己没有值就沿 `parentId` 往上找（异色跟它普通颜色那一版同价）；一路到顶都没有则用兜底值。
- **兜底值是 3000**（星光值那个兜底是 80）。取值依据：390 只本体基础形态的洛克贝分布是 1200 / 1800 / 2100 / 2400 / 3000 / 3150 / 4200 / 4500 / 6000 这 9 档，**中位数正好是 3000**，拿它当兜底不会把平均值带偏。同样不能给 0 —— 会出现「抽到首领化获得 0 洛克贝」这种看着像坏掉的结果。
- 洛克贝缺失的面比星光值更宽：**814 只里有 136 只没有**（64 只首领化全部没有、36 只本体、1 只地区形态，另有 35 只异色跟着它们没值）。往上找到顶还是 136 只里的 91 只。
- **洛克贝的加成跟星光值的加成不是一套，别复用**：异色 **×10**、每有一个形态标签（地区形态 / 首领化各算一个）再 **×2**。即：单形态 ×2、首领化+地区形态 ×4、异色 ×10、异色+首领化 ×20、三个标签叠满 ×40。同样**不封顶**，理由跟星光值那条一样。
- 两个倍率要**分开存**（`starMultiplier` / `rocoMultiplier`），因为规则不同、以后还可能各改各的。老记录两个都没有，各自用「进账 ÷ 图鉴基础值」反推。**能反推出的倍率集合也不一样**：星光值是 `{1,2,4,8}`，洛克贝是 `{1,2,4,10,20,40}`（异色那档是 ×10 不是 2 的幂，所以没有 8），两张表别互相复用。
- 池子里另外还挂着 `rocoShinyMultiplier`（10 或 1）和 `rocoFormMultiplier`（1/2/4）两个字段，**只给 tooltip 拆解加成用**，抽奖结算用的是合起来的 `rocoMultiplier`。前端拿这两个数写「异色 ×10 · 首领化 ×2」这种说明（见 7.8）。
- 头像在 `images/heads/`，立绘在 `images/art/`（非异色）和 `images/shiny/`（异色），由后端挂一个静态目录（`/spirits`）直接给前端用。
- 名单在**服务启动时读一次就定下来**，之后不再碰磁盘。图鉴基本是固定的（大概两个月才更新一次），不值得每次抽奖都去 statSync 看文件改没改。采集脚本更新了数据之后要**重启服务**才生效（不想重启就调 `reloadSpirits()`）。
- 头像文件缺失的精灵**照样进池子**，前端图片加载失败时用占位图兜底。不因为少一张图就把精灵踢出池子——不然图片没拷全的时候池子会悄悄变空。

7.7 不放回（每天重置）：
当天已经抽到过的**实体**（按 `id`）不会再抽到，等价于**不放回**地从当天的精灵池里抽。
已抽记录按天存，跨天自动清空，第二天重新从整个池子里抽（同一只精灵昨天抽过，今天照样能再抽到）。
把当天的精灵全抽完之后，再点「完成」会提示「今天的精灵都抽完了」。

7.8 抽到的展示（一律显示**洛克贝**，不显示星光值）：
- 抽到的那一刻，屏幕底部浮出一个**小浮窗**：左边**头像** + 右边精灵名称 + 编号 + 本次获得的洛克贝（倍率用 `1800×10` 的小标跟在后面，语义见下面那几条）；这一次刚好够档位凝结了许愿星的话，文案末尾再补一句「凝结出 N 颗许愿星」（不提消耗了多少星光值）。几秒后自己淡出，不挡住连续点「完成」。用的是共用的 `components/Toast.vue`（见第 2 条），不再是页面里那块内嵌结果卡。
- 星光值页中间（进度条之后、任务列表之前）有一块「今日抽到的精灵」，用图鉴那种小卡片平铺展示当天抽到的每一只：头像 + 编号 + 名称 + 洛克贝。只显示当天的，跨天清空。
- **点任意一张小卡片，弹出一个详情框**，显示这只精灵的完整信息：**立绘（1024×1024 原图）+ 名称 + 编号 + 属性 + 分类 + 洛克贝 + 形态标签 + 精灵介绍**。形态标签说明它是基础形态 / 地区形态 / 首领化 / 异色（同时是首领化和地区形态的两个都标）。立绘是本地文件，点开就有，不转圈。
- **异色的小卡片用异色立绘**（`images/shiny/` 里那张），不用头像。原因：wiki 没给异色单独的头部特写，**193 只异色的头像跟本体是同一张图**，名字也逐字相同（异色在 wiki 上不是独立条目，只是同一张卡多挂一张立绘）。卡片上要是也用头像，异色和本体就长得一模一样、名字也一样，看起来像重复抽到了同一只。其余精灵照旧用 11KB 的小头像。
- 异色角标用 **wiki 自己的那张「异色外观」图标**（57×56，从精灵详情页立绘切换那排 tab 里拿的）。193 只异色**共用同一张**，`alt="异色外观"`，不能跟异色立绘混为一谈——立绘每只都不一样，这个图标是「这只是异色」的官方标志。图已存进项目：`frontend/src/assets/shiny-icon.png`（原图 `https://patchwiki.biligame.com/images/nrc/5/5a/bsfn3nrdt2bgkjsl7dnptr9rumxxfhj.png`）。名字后面再补「（异色）」，双保险。地区形态和首领化的名字本身带「（蓬松的样子）」这类后缀，不用额外标注。
  图标是灰色线稿，放深色卡上看不见，所以垫一层金底、把线稿压成深色。**`filter` 要加在里面的 `<img>` 上，不能加在金底那层 `<span>` 上**——`filter` 会把元素自己的背景一起算进去，加在外面金底也会被 `brightness(0)` 一起压黑，变成一个黑方块。
- **洛克贝翻了倍的话，小卡片和详情弹窗上显示的是图鉴上的基础值，加成靠后面一个 `×N` 小标表示**：写成 `1800 ×20`（不写成 `36000 ×20`）。原因有两个：一是小卡片那个位置放不下「36000 基础 1800×20」两截数字，二是只写个 `×20` 跟在 36000 后面会被读成「36000 再翻 20 倍」，而图鉴上明明写的是 1800 —— 显示基础值 + 倍数，两个数都能和图鉴对上。基础值是前端 `roco / rocoMultiplier` 除回去算的，不用后端再发一个字段；**但除数必须是记录里存的那次倍率**，不能按当前规则重算（见 7.6）。
  **这里的 `×N` 是异色和形态两笔乘完的总倍数**（异色 ×10 和形态 ×2 是可以同时生效的，见 7.6），不是单独哪一个。所以 tooltip 里要把两笔拆开写清楚，只说一个 `×20` 看不出这 20 是怎么来的。
- **结果卡是唯一例外，照旧写实际进账的数**：`+36000 洛克贝` 后面跟 `1800×20`。它本来就是一句「这次加了多少钱」的记账（`+` 开头），写基础值等于报错账；数字对不上时这个 `1800×20` 就是解释。所以几个地方的数字不全部一样是有意的，不是漏改。
- tooltip 写「图鉴 1800 洛克贝，异色 ×10 · 首领化 ×2，本次获得 36000 洛克贝」——只有一笔时就不写另一笔（「图鉴 1800 洛克贝，异色 ×10，本次获得 18000 洛克贝」）。
  **这两笔是后端给的两个字段**（`rocoShinyMultiplier` / `rocoFormMultiplier`，见 7.6），但后端**只在两笔乘起来正好等于记录里那个总倍率时才给**，否则两个字段给 `null`，前端退回笼统写法「{形态标签} ×20」。防的是这种情况：以后只改了异色那档的规则，老记录存的总倍率是旧规则算的（×20），而池子给的两笔是新规则的（×10 和 ×2），拼起来就成了「异色 ×10 · 首领化 ×2，本次获得 18000 洛克贝」——数字对不上账的说明比没有说明更糟。
- 流水文案带上精灵名：`抽到「迪莫」获得 1800 洛克贝`；翻倍时补一句 `（形态标签 ×N）`，不然流水上的数比图鉴大，看着像算错。
- **改版之前抽到的记录里没有 `roco`**（那时候只记星光值）。这种记录的 `roco` 是 `null`，**整行洛克贝不显示**，而不是兜底成 0 —— 那次抽卡进的本来就是星光值，补一个洛克贝出来等于凭空记账。这些记录本来也不该再出现在页面上（当天抽的除外，跨天就清了）。
- **洛克贝图标**用的是 wiki 上那个金币（`alt="洛克贝"`，128×128），跟异色图标一样扒下来存进项目：`frontend/src/assets/roco-icon.png`（原图 `https://patchwiki.biligame.com/images/nrc/1/10/blxvp7k90uq3p8prz24feerler3yfsi.png`）。它出现在总览卡标题、小卡片、详情弹窗、流水金额前面好几处高度不一样的地方，所以 CSS 用 `vertical-align` 让它跟着字走，不用 flex。

7.9 采集脚本要补 `roco` 字段（跨仓库改动）：
洛克贝这一项**wiki 详情页上有，但 `nrc-scraper` 的采集脚本没抽**，所以先得把它加进去。好在详情页 HTML 是**原样存档**的（`data/pages/*.html.gz`，当初就是为了「以后加字段不用重新访问 wiki」），所以这一步是**纯离线**的，不用再爬一遍 wiki。

要动的地方（都在 `C:\data\code\nrc-scraper`）：
1. `scrape-pages.mjs`：照 `parseStar()` 的写法加一个 `parseRoco()`。两个 `roco-pill` 的结构完全一样，只是 `img alt` 从「星光值」换成「洛克贝」。同样带 `rocoFound`。
2. **加一条离线重新抽取的路子**。现在 `scrape-pages.mjs` 只会在 wiki 上跑（断点续传是「跳过已完成的」，重跑不会重新解析存档），所以要么给它加一个模式，要么单独写个脚本把 `data/pages/*.html.gz` 重解析回 `pages.json`。**光在网络那趟里加字段是没用的** —— 不重跑一次就永远只是 `undefined`。
   实际做法是给它加了个 `--from-cache` 模式（`node scrape-pages.mjs --from-cache`）：读存档逐个重解析，**整份重写** `pages.jsonl` + `pages.json`（不是追加，追加会把同一个 id 写进去两遍）。顺手把网络那趟和这趟共用的那段抽成了 `extractRow()`，免得两处解析逻辑慢慢走偏。
3. `build-entities.mjs`：把 `roco` / `rocoFound` 跟 `desc` / `kicker` / `star` 一样带进实体表；异色共用所属卡片的洛克贝，跟 `star` 的处理一致。
4. `README.md`：字段表补 `roco` / `rocoFound`，「数据概览」补覆盖率。**README 是格式口径的来源**，改了字段就得改它。
5. 重跑后**必须 diff 一遍新的 `entities.json`**，确认除了多出 `roco` / `rocoFound` 之外没有任何别的字段变动 —— 重建脚本要是有漂移，会把别的数据一起改掉。

**当前实测的覆盖率**：621 个详情页里有 **520 页两个 `roco-pill` 都在、101 页两个都没有**（一个不差地重合），所以洛克贝和星光值是同一块模板、同进同出。814 个实体里最终 **678 只有值、136 只没有**。
